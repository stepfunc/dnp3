`OutstationApplication` is how the outstation asks your application for what only it knows, and tells it about changes
worth saving. Each callback covers one job:

| Job | Called when | What your code does |
|-----|-------------|---------------------|
| [IIN bits](#iin-bits) | The outstation builds a response | Reports the state of your device |
| [Time synchronization](#time-synchronization) | The master writes the time | Sets the clock, if it accepts the master's time |
| [Restarts](#restarts) | The master asks for a cold or warm restart | Usually reports that restarts aren't supported |
| [Counter freezes](#counter-freezes) | The master freezes counters | Copies counters to frozen counters |
| [Saving changes](#saving-what-the-master-changes) | The master writes deadbands, event classes or device attributes | Saves them so they survive a restart |
| [Event confirmations](#event-confirmations) | The master confirms events | Tracks which events were delivered, if it needs to |

## IIN bits

The outstation calls `getApplicationIin()` for every response and merges your bits with the ones it manages itself. You
control four:

* `needTime`: the outstation needs time synchronization
* `localControl`: some output points are in local mode
* `deviceTrouble`: the device has a problem
* `configCorrupt`: the device configuration is corrupt

## Time synchronization

Whichever procedure the master uses, the outstation calls `writeAbsoluteTime(..)` with the time in milliseconds since
January 1st, 1970, 00:00:00 UTC.

Set `needTime` when your clock needs synchronizing, typically at an interval that depends on its accuracy, and clear it
**in** `writeAbsoluteTime(..)`. If the bit is still set in the response, the master assumes the synchronization failed, and
some masters then write the time over and over.

An outstation that gets its time from another source, such as NTP or IRIG-B, usually rejects the master's time unless that
source is unavailable. One that doesn't support time synchronization at all returns `NOT_SUPPORTED`.

## Restarts

A master can ask the outstation to restart. Because an attacker could use this to take a device offline, we recommend
returning not supported from `coldRestart` and `warmRestart` in most products, and always in software gateways that share
a server with other services. If you must support restarts, for conformance tests or a customer requirement, return an
estimate of how long the restart takes; masters make little use of it, so it needn't be accurate. The outstation never
restarts on its own: your application does.

## Counter freezes

When the master freezes counters, use the `DatabaseHandle` you're given to copy each counter to its frozen counter, and with
`FREEZE_AND_CLEAR`, also reset the counter to 0. Requests to freeze at a given time and interval are passed to your
application too.

## Saving what the master changes

A master can change three kinds of settings in the outstation. The outstation applies each change to its database itself;
the callbacks let you save it to non-volatile memory and apply it again when you add your points at startup. An outstation
that doesn't save them returns to its configured values when it restarts.

| Setting | Callbacks | Notes |
|---------|-----------|-------|
| Analog input deadbands | `beginWriteAnalogDeadBands`, one call per deadband, `endWriteAnalogDeadBands` | Rejected unless `supportWriteAnalogDeadBands` returns true |
| Event classes | `beginAssignClass`, one call per point header, `endAssignClass` | Processed unless `supportAssignClass` returns false |
| Device attributes | One call per attribute written | Only for attributes you define as writable |

Save each batch in its end callback. A new event class applies only to events created afterwards.

An attribute write callback can reject a value, for example one out of range, by returning false. The outstation itself
rejects writes to attributes that aren't defined or writable, or whose type doesn't match.

## Event confirmations

When the master confirms events, `eventCleared` reports each one delivered, by the ID its update returned. Most applications don't need
this; it helps when the source of the events wants to know which ones have been delivered.
